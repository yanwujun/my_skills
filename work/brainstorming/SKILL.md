# Brainstorming：将想法转化为设计

<HARD-GATE>
设计批准前不写代码、不搭项目。角色是理解需求，不是构建。
</HARD-GATE>

## 反模式："这太简单了，不需要设计"

每个项目都过此流程。设计可以很短，但必须呈现并获批。

## 检查清单（按顺序）

1. **探索上下文** — 文件、文档、最近提交
2. **澄清问题** — 一次一个，目的/约束/成功标准
3. **2-3个方案** — 附权衡和推荐
4. **呈现设计** — 每部分后获取批准
5. **写设计文档** — 保存并提交
6. **规格自审** — 占位符/矛盾/歧义/范围
7. **用户审查** — 继续前要求审查spec
8. **审查就绪** — 需求已理解，可进行代码审查

## 关键原则

- **一次一个问题** — 不要压倒人
- **优先选择题** — 比开放式容易回答
- **YAGNI** — 无情移除不必要功能
- **探索替代方案** — 确定前提2-3个方案
- **渐进式验证** — 呈现→批准→继续

## 领域对齐

- 术语收紧：模糊时提出精确术语
- 对照已有语言：冲突时指出
- 构造场景：探测边界情况

## 规格自审

1. 占位符扫描：TBD/TODO → 修复
2. 内部一致性：有矛盾吗
3. 范围检查：聚焦到一个实现计划？
4. 歧义检查：能否两种解释？
5. 可追溯：每个需求有验收标准？
