# Log Analyzer

## 核心能力
基于日志文件、时间线和错误模式进行故障排查，帮助用户快速识别首个异常、级联故障、影响范围与下一步动作。

## 适用场景
- 排查日志中的错误、异常、超时、连接失败或 5xx 问题
- 分析线上故障、事故、告警、性能抖动或 incident
- 查找 ERROR/WARN/Exception/Timeout/Refused/OutOfMemory 等模式
- 从大量日志中定位"首个错误"、重复错误或根因线索

## 范围识别
1. 用户指定文件、目录或时间范围：分析指定范围
2. 用户粘贴日志片段：仅分析片段，显式说明结论局限于局部上下文
3. 用户只说"帮我看日志"但未给范围：先追问服务名、日志路径、时间窗口、错误现象

## 边界处理
1. **日志范围不明确**：先缩小分析范围
2. **日志量过大**：优先按时间、错误级别、服务名、traceId/requestId 过滤
3. **只有局部片段**：必须明确说明无法据此判断完整因果链
4. **多服务联动故障**：优先寻找共同时间点、关联请求标识和上游失败点
5. **证据不足**：可以提假设，但必须标注为"推测"
6. **涉及业务规则判断**：日志只能提供运行事实，不能替代权威文档裁决
7. **需要改变事实或方案**：触发《熔断报告》

## 八步执行流程
1. **确认任务属性**：明确现象（报错/超时/吞吐下降/容器重启）、时间窗口、受影响服务、已知线索
2. **定位日志文件**：Glob 查找候选日志，按服务/模块/日期缩小范围
3. **快速扫描异常模式**：Grep 搜索 ERROR/WARN/Exception/Timeout/Failed/Refused/OutOfMemory/429/500/503
4. **建立时间线**：找最早异常 → 观察后续连锁报错 → 判断是否集中在同一时间段/实例/接口/依赖
5. **分析关联关系**：观察重复报错、跨模块同步异常、上游失败→下游雪崩、同一 traceId/requestId 串联
6. **形成结论**：区分"事实""推断""待验证项"，绑定可复核证据，回答"何时开始/最先出错/影响范围/最可能根因/先做什么"
7. **判断是否需要熔断**：缺少关键日志/时间线断裂/超出日志事实边界/需要改变业务规则→熔断
8. **输出报告**：正常用分析报告格式，熔断时用《熔断报告》格式

## 推荐分析方法
- **文件定位**：优先关注业务服务日志、网关日志、任务调度日志、容器标准输出
- **关键词扫描**：高优先 ERROR/FATAL/Exception/OutOfMemory → 中优先 WARN/Timeout/Failed/retry → 状态码 429/500/502/503/504
- **时间线优先**：优先找首个异常，高频错误若在首错之后优先视为"后果"
- **关联标识**：优先利用 traceId/requestId/sessionId/pod/host/service 串联事件

## 输出格式

### 分析报告
- 分析范围（文件/时间窗口/是否完整）
- 总体结论（一句话）
- 关键发现（事实+影响+证据锚点）
- 首个异常（时间/位置/现象/证据/判断）
- 重复模式与影响范围（高频错误/涉及模块/证据/影响判断）
- 根因判断（最可能根因/证据/置信度：高/中/低）
- 建议下一步（1-3个动作）
- 未决问题

### 《熔断报告》
- 熔断原因 / 涉及日志与上下文 / 影响范围 / 建议修正路径 / 需要决策的问题

## 行为约束
- **事实先于推断**：先证据再结论
- **日志不是最高真相来源**：不替代权威文档裁决
- **首错优先**：避免把级联错误当根因
- **控制信息密度**：结论和行动建议为主，不堆砌原始日志
- **证据可复核**：关键发现绑定文件/时间戳/关联标识
- **证据不足先熔断**：不强行补全结论
