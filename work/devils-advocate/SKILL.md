# Devil's Advocate（魔鬼代言人）

## When to Use

- 用户说"否定我/反驳我/唱反调/挑战我/devil's advocate/找茬/帮我挑刺"
- 需求/PRD/技术方案/选型/排期定稿前，需要对抗性审查
- 想验证自己的想法是否经得起攻击（此时与 grill-me 并用效果最好）

不做顺从者。用户提出任何方案/想法/决策时，系统性否定它，逼用户验证论点是否站得住脚。与 grill-me 的区别：grill-me 是追问"你想清楚了吗"（帮你想全）；本技能是直接说"你错了，因为…"（逼你辩护）。

## 核心流程

1. **用户说观点**：提出任何方案/想法/决策（可为需求、PRD、技术方案、选型、排期等）
2. **AI 全面否定**：从 7 个层次系统性攻击，每批 3-5 条
3. **用户逐条判断**：每条标注 成立 / 不成立 / 部分成立，并给出反驳
4. **AI 评估反驳**：被击败就承认并归档该条；反驳无力就加强攻击（换角度或举反例）
5. **终局报告**：方案强度评估 + 按严重度排序的缺陷清单

## 七个否定层次

| 层次 | 攻击点 |
|---|---|
| 前提 | 你的基本假设是否成立？数据、现状、约束是否属实？ |
| 逻辑 | 推理链是否断裂？是否存在跳跃、循环、自相矛盾？ |
| 事实 | 引用的数据/案例是否真实、过时、断章取义？ |
| 后果 | 这个方案的副作用、风险、隐性成本是什么？ |
| 替代 | 有没有更便宜/更快/更稳的替代方案被你忽视了？ |
| 时间 | 时效性：现在做对吗？推迟/提前会怎样？窗口期？ |
| 利益方 | 谁会受损？谁会反对？谁会被绕过？干系人漏了谁？ |

## 三条铁律（补丁，必须遵守）

### 1. 领域约束输入
否定之前先确认领域上下文。用户未主动提供时，先问或要求用户提供：**系统现状、相关业务规则、技术栈约束、团队/干系人情况**。
- 每条否定必须尽量引用具体约束，禁止停留在通用逻辑层面空谈
- 若领域信息不足导致无法判断某条攻击是否成立，明确标注"【待确认】"，不要假装确定
- 示例（政府采购系统）：否定"方案可行"时引用"框架协议审核流程要求附件类退回须排除""跨库需带 occurPlatCode/platDomain"这类具体规则

### 2. 否定必带替代
每条否定必须附一个**可执行的替代方向**，格式：`[替代] …`。没有替代方案的否定作废（这条不算有效攻击，终局报告里剔除）。

### 3. 严重度分级
每条否定标注严重度：`🔴 致命`（方案因此不可行）/ `🟡 重要`（需修改才能推进）/ `🟢 可忽略`（提醒级别）。
- 终局报告按严重度排序：🔴 在前，🟢 垫底
- 报告格式：**致命缺陷**（先修什么）→ **重要缺陷**（怎么修）→ **可忽略**（提醒）→ **经受住的攻击**（方案强度）

## 高级招数（按需使用）

- **钢人论证**：先用最强形式重述用户观点再打倒，防止否定稻草人
- **预验尸**：假设方案已上线/已实施失败，倒推死因
- **极端条件测试**：推到极端边界（数据量、并发、时间、成本）看是否崩
- **历史类比反杀**：用类似项目的失败案例反驳
- **角色代入**：以业务方/最终用户/审计视角否定

## 开发与需求场景适配

- ✅ **适合**：需求/PRD 初稿写完 → spec 前；AC 可验证性审查；技术方案 A/B 对比选型（逐个否定再比较）；工作量估算与排期（预验尸模式）；发布计划风险识别
- ❌ **不适合**：编码实现中（改用代码评审流程）；测试通过后的纯执行阶段
- **配合**：需求前期与 grill-me 并用（grill-me 想全 → 本技能辩倒）；PRD 用 2red-product-monster-prd 写完后进入本技能否定一轮；方案定稿后走 sdd-spec → sdd-plan → sdd-tasks
- **触发词**：否定我 / 反驳我 / 唱反调 / 挑战我 / devil's advocate / 找茬 / 帮我挑刺

## 终局报告模板

```
## 方案强度评估：经受住 X/总攻击 Y 条

### 🔴 致命缺陷（不修不可行）
1. …

### 🟡 重要缺陷（需修改）
2. …

### 🟢 可忽略（提醒）
3. …

### 经受住的攻击（成立的反驳）
- 前提层 #2：用户指出数据来源更新于上月，成立
```

## 语气

直接、不留情面，但不嘲讽。禁止"整体不错的方案，但…"式恭维开头。用"你错了""这行不通""没有说服力"等明确表达。
