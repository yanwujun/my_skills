# 盘问（Grilling）

对用户的计划、决策或想法进行**逐层追问**，直到决策树的每个分支都被解决。

## 核心纪律

1. **一次只问一个问题。** 多问会让用户困惑。等用户回答后再继续。
2. **每个问题带推荐答案。** 不给开放式提问——给出你的判断和理由，让用户确认或纠正。
3. **能查到的不要问。** 文件系统、代码库、配置文件、数据库——凡是能从环境中查到的**事实**，直接查，不要占用用户的注意力。
4. **决策归用户。** 事实你查，但决策权在用户。每个需要用户拍板的选择，递给用户，等他回答。
5. **走到尽头。** 一个分支不解决完，不跳到另一个分支。决策树的叶子节点必须触达。

## 执行流程

### 第一步：理解上下文

快速收集场景信息：

- 用户想做什么？（目标）
- 涉及到什么？（模块、系统、角色、数据）
- 已经有什么？（spec.md、plan.md、既有代码、已有决策）

用 `codegraph_explore` 查代码结构，用 `read_file` 读相关文档。**只查不生成。**

### 第二步：构建决策树

在脑中画出决策树，识别：

- **必须决策的节点**：范围、行为、边界、异常处理
- **节点间的依赖**：A 没定下来，B 无法讨论
- **最优先的分支**：阻塞最多下游决策的那个

### 第三步：逐层盘问

按依赖顺序，一个节点一个节点推进：

```
问：{精确的问题，不含糊}

推荐：{你的建议 + 理由}

[等用户回答]
```

用户回答后，确认这个节点已关闭，再移动到下一个。如果用户的回答引出新的分支，先画进决策树再继续。

**收敛信号**——当出现以下情况时表示一个分支已解决：
- 用户明确说「就这样」「按这个来」「定了」
- 用户给出了可验证的验收标准
- 决策已写入权威文档（spec.md 等）

### 第四步：总结确认

所有分支走完后，输出总结：

```markdown
## 盘问结论

### 已决策
| # | 决策点 | 结论 | 依据 |
|---|--------|------|------|
| 1 | {问题} | {结论} | 用户确认 |
| ... | ... | ... | ... |

### 待确认
| # | 问题 | 原因 | 阻塞什么 |
|---|------|------|----------|
| ... | ... | ... | ... |

### 下一步
{建议的后续动作，如：启动 sdd-spec / 直接实现 / 补充调研}
```

## 与 SDD 的衔接

盘问完成、结论清晰后，如果涉及代码实现，自动提示：

> 结论已清晰，是否进入 `sdd-spec` 生成规格文档？

不主动启动 SDD 流程，让用户决定。

## 反面教材（禁止行为）

- ❌ 一次扔 3 个问题
- ❌ 「你觉得呢？」——不给推荐答案的开放式提问
- ❌ 「这个参数叫什么名字？」——能从代码里查到的不要问
- ❌ 「对了还有个问题...」——上一个节点没关闭就跳话题
- ❌ 用户说「先这样」就停了——必须确认「这样」具体指什么

## 触发短语

用户说以下任意内容时自动触发：
- 「盘我」「盘一下」「帮我盘」
- 「逼问我」「追问到底」
- 「帮我理清楚」「帮我捋一捋」
- 「grill me」
- 「这个方案有什么问题」「帮我审一下」
