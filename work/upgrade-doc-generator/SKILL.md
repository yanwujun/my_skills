# 升级说明文档生成器

为 P2040 直采与框架协议项目生成标准化升级说明文档。根据用户提供的修改信息，生成符合现有文档格式规范的 md 文件。

## 触发条件

用户说"生成升级文档"、"写升级说明"、"帮我生成版本升级文档"等。

## SVN 日志拉取（自动模式）

当用户未提供具体修改内容，但给出了分支名或 SVN 路径时，自动从 SVN 拉取提交日志来生成文档。

### 命令

```bash
# 获取分支的修改日志（相对于 trunk 或指定起始版本）
svn log -v -r {起始版本}:HEAD {SVN路径}

# 常见用法：获取某个分支的所有提交
svn log -v --stop-on-copy {branches/xxx}

# 限制数量
svn log -v -l 30 {SVN路径}
```

### SVN 仓库根路径

```
https://192.168.2.10:8080/svn/GovProEleTrade/P20高效电子交易/P2040直采与框架协议/
```

### 日志解析规则

1. 过滤掉 merge 提交（含 "Merge"、"合并" 关键字的记录降权或忽略）
2. 按提交信息归纳修改类型：`后端接口` / `前端页面` / `SQL` / `配置文件` / `Bug修复`
3. 同一文件的多次提交合并为一条修改点
4. 提交人/时间作为辅助信息，不写入文档正文

### 使用方式

```
svn log -v -l 30 --stop-on-copy \
  https://192.168.2.10:8080/svn/GovProEleTrade/P20高效电子交易/P2040直采与框架协议/C1后端服务/电子直采/branches/{分支名}
```

拉取后根据日志内容推导：
- **修改了哪些服务**（根据 SVN 路径判断：`C1后端服务/电子直采` = xcj-ezc，`行采家trade` = xcj-trade）
- **是否为纯后端/bug修复/含前端**（根据涉及的路径判断）
- **是否有 SQL**（含 `.sql` 文件变更则标记）

### 信息补全

日志拉取后仍缺失的信息（分支名、测试域名、版本号、SQL文件具体路径等），需向用户确认。

## 文档路径规则

```
D:\项目\svn\P2040直采与框架协议\版本管理\{模块}\{版本号} {功能描述}\升级说明文档.md
```

- 模块：`直采商城(新）`（zc-mall）或 `框架协议`（kjxy）
- 版本号格式：`x.y.z`，如 `1.26.9`
- 功能描述：简短中文，如"订单负数数量适配"

## 模式一览

| 模式 | 触发词 | 适用场景 |
|------|--------|----------|
| **简约**（默认） | "简单的"、不指定 | 快速生成，只有修改点+SQL+程序 |
| **详细** | "详细点"、"完整版" | 含改造内容+接口+测试要点+发布顺序 |
| **Bug修复** | "修复文档"、"bug" | 问题现象→根因→修复要点→测试 |
| **新平台上线** | "新平台"、"区县" | 注意事项+SQL序列+Nginx配置 |
| **自动（SVN日志）** | 未给修改内容但给了分支名/SVN路径 | 自动拉取svn log，解析后生成 |

### 简约模式（默认除非用户明确指定）

触发词："简约模式"、"简单的"、"只要修改点"、"概要版"

| 章节 | 内容 |
|------|------|
| 标题 | `# {模块} v{版本号} — {功能描述}` |
| 版本信息表 | 版本 / 分支 / 测试环境 |
| 升级概述 | 一句话 |
| 修改点清单 | 类型/修改项/涉及服务/说明 表格 |
| 升级SQL | 类型/执行范围/脚本路径 表格 |
| 发布程序 | 序号/类型/SVN地址/说明 表格 |

**不生成**：改造细节、页面截图、测试要点、接口详情、发布顺序、配置变更

### Bug修复模式

触发词："bug修复"、"修复文档"、"问题修复"

专用于修复线上问题。章节：

1. 标题 + 版本信息表
2. 一、问题现象 — 用户可见表现
3. 二、根因说明 — 技术原因（列表）
4. 三、修复要点 — 表格：序号/修复内容
5. 四、升级SQL（无则写"无"）
6. 五、发布程序 — 仅后端（bug修复一般不改SQL/前端）
7. 六、测试要点 — 表格：编号/场景/操作要点/通过标准（比功能测试更细）

参考：框架协议 `1.26.6.1`（支付撤回Bug）

### 新平台上线模式

触发词："新平台"、"区县上线"

结构参考南岸/万州等文档：

1. 注意事项（参数确认清单）
2. 升级内容（一句概述）
3. 添加市场（管理端操作）
4. 数据库升级（SQL序列，编号列表）
5. 发布前配置（Nginx/域名等）
6. 发布程序

### 详细模式

触发词："详细模式"、"详细的"、"完整版"、"带测试"、"详细点"

| 章节 | 内容 |
|------|------|
| 标题 + 版本信息表 | 同简约 |
| 一、升级概述 | 整体说明 + 覆盖范围（1-3句） |
| 二、修改点详情 | 按功能点分组，每个含：功能说明/端/路由/接口/改造内容/验证环境 |
| 三、升级SQL | SQL脚本清单表 + 简要说明 |
| 四、配置变更 | 仅当有配置变更时出现，含配置中心/示例 |
| 五、发布程序 | 程序清单表 + 发布顺序表 |
| 六、测试要点 | 编号/场景/预期 表格 |

## 格式规范

### 表格对齐

- 序号列、状态列用 `|:----:|`（居中）
- 说明/路径列用 `|------|`（左对齐）

### 言简意赅原则

1. 功能说明不超过 2 句话
2. 改造内容用要点列表，每条不超过 1 行
3. 禁写价值描述（"提升了用户体验"、"优化了性能"）
4. 禁写实现细节（"在 xxxService 中新增方法"），除非用户明确提供
5. 接口只写 Method + Path + 关键字段，不写完整 JSON

### 路径/URL 规范

- SVN 地址为完整 HTTPS URL，用反引号包裹
- SQL 脚本路径用相对路径：`{脚本文件名}.sql`
- 图片用 `![描述](image-xxx.png)`

## 生成流程

1. **判断模式** — 有分支名/SVN路径但无修改内容 → 自动模式；有修改内容 → 按用户指定模式
2. **自动模式：拉取日志** — `svn log -v -l 30 --stop-on-copy {SVN路径}`，解析提交信息
3. **收集信息** — 检查是否包含：模块、版本号、功能描述、修改内容、分支名、SVN地址。缺失则主动询问。
4. **确认模式** — 未指定时默认简约；用户说"详细"等则切换
5. **生成文档** — 按模板输出到正确路径
6. **告知用户** — 输出文件路径，询问是否需要调整

## 批量汇总已有升级文档 → Excel

当用户要求"总结所有版本的修改点"、"生成升级汇总Excel"等，读取指定目录下所有版本的 `升级说明文档.md`，汇总为 Excel 表格。

### 目录结构

```
D:\项目\svn\P2040直采与框架协议\版本管理\{模块}\{版本号} {功能描述}\升级说明文档.md
```

- 模块：`框架协议` 或 `直采商城(新）`
- 排除 `历史汇总` 子目录（已归档的旧版本）
- 部分版本可能只有 `升级说明文档.pdf` 无 `.md` 文件

### 工作流程

1. `search_files` 搜索所有 `升级说明文档.md`，排除 `历史汇总`
2. `execute_code` 批量 `read_file` 读取所有文档
3. 从文档提取：版本号、修改点、SQL、发布范围、测试要点
4. 从文件/目录 mtime 获取升级日期（文档内通常不写日期）
5. 用 `openpyxl` 生成 Excel（5列：版本号/升级日期/类型/修改点摘要/详细修改说明）

### 重要：默认生成详细版

用户说"总结修改点"时，默认生成**详细版**而非简约版。每个修改点展开到：
- 具体接口名/字段名/参数值
- 流程步骤（如 MQ→轮询→落库）
- SQL 表名和字段
- 发布分支和模块范围
- Bug类需含根因

不要只写一句概括——那会让用户追问"能详细一点吗"。宁愿第一次就详细。

### Excel 格式

| 版本号 | 升级日期 | 类型 | 修改点摘要 | 详细修改说明 |
|--------|----------|------|-----------|-------------|
- 冻结首行，启用自动筛选
- 行高自适应（详细说明列通常 200+ 像素）
- 日期从目录 mtime 获取，格式 `YYYY-MM-DD`
- 输出路径：`D:\平时处理文件\{年月}\{模块}\{模块}升级汇总_{起始版本}至{结束版本}.xlsx`

参考已有汇总文件 `references/文档清单.md` 了解最新版本概况。
