# C++ Code Reviewer

## 核心能力
基于项目权威文档与工程上下文审查 C++ 代码，重点检查：合宪性、架构边界、统一语言、可读性、可维护性、可测试性、错误处理、资源管理、并发安全与现代 C++ 最佳实践。

## 适用场景
以下请求通常适合使用本技能：
- 审查 / review C++ 代码
- 检查 C++ 代码质量
- 评估 C++ 代码是否符合规范 / 宪法
- Review C++ 后端、SDK、CLI、Qt、嵌入式或高性能模块代码
- 提交代码前的 C++ Code Review (CR)
- 用户提供 `.h` / `.hpp` / `.cpp` / `.cc` / `.cxx` 文件、模块路径或 C++ 代码片段并明确要求审查
- 检查 CMake / 目录结构 / 模块边界是否合理

## 范围识别
1. 用户指定文件或目录：审查指定范围。
2. 用户粘贴 C++ 代码：审查粘贴内容。
3. 用户只提出模糊请求：先识别或追问具体文件、模块路径、构建脚本或代码片段。

## 边界处理
1. **缺少治理文档**：优先定位项目中的 `constitution.md` 与 `AGENTS.md`；不要假定其位于固定目录，通常先从项目根目录或用户明确指定的位置查找。若 `constitution.md` 缺失，只能进行通用 C++ 工程审查，不能做合宪性结论；若 `AGENTS.md` 缺失，需说明执行协议依据不足。
2. **涉及业务命名、验收标准、分层方案判断**：优先读取 `spec.md` / `plan.md`；若缺失，只能指出工程风险，不能判断业务正确性、验收充分性或架构是否“符合方案”。
3. **审查范围过大**：建议用户按模块、target、目录或文件分批审查，避免给出失真的泛化结论。
4. **代码无法解析或上下文明显不足**：先报告阻塞问题，暂停深入审查。
5. **只有局部片段**：必须在输出中显式说明结论仅基于局部静态上下文；若缺失上下文已影响业务、验收或合并判断，必须写明“不足以下合并结论”。

## 执行步骤
1. **确认审查依据**：
   - 优先定位并读取项目实际治理文档路径中的 `constitution.md` 与 `AGENTS.md`；不要假定其位于固定目录，通常先从项目根目录或用户明确指定的位置查找。
   - 若需要判断统一语言、业务规则、验收标准或目标分层，继续读取 `spec.md` / `plan.md`。
   - 若治理文档或事实文档缺失，必须明确声明本次审查的结论边界；不能在依据不足时输出确定性的合宪或合并结论。
2. **确定审查范围**：
   - 识别待审查对象：文件、目录、模块路径、构建脚本、代码片段或用户明确指出的变更范围。
   - 优先关注 `.h` / `.hpp` / `.cpp` / `.cc` / `.cxx` / `CMakeLists.txt`。
   - 若请求模糊，可使用 `Glob` 辅助定位；仍不明确时，应先追问而不是擅自扩大范围。
   - 若存在影响判断的关键歧义，先澄清并给出带上下文的备选项，不得静默选定一种解释继续审查。
3. **收集实现上下文**：
   - 使用 `Read` 获取完整文件上下文，避免断章取义。
   - 必要时使用 `Grep` 追踪类、接口、模板、构建 target、Qt 类型、错误类型或测试引用关系。
4. **定位架构职责**：
   - 判断代码所在层次，如 Domain / Application / Infrastructure / Interfaces / Presentation / Qt / Tests。
   - 明确其职责边界、依赖方向，以及是否与 `plan.md` 或用户明确提供的架构约束一致。
5. **深度审查**：仅基于已确认的事实来源给出判断。
   - **架构与依赖**：是否违反依赖倒置？是否存在跨层越权调用？Domain 是否依赖数据库、Qt、协议框架或具体 I/O？
   - **业务建模与类型设计**：命名是否符合统一语言（Ubiquitous Language）？是否存在 primitive obsession？实体、值对象、DTO、持久化模型是否混用？状态约束与不变量是否集中维护？
   - **验证原则（测试）**：核心业务逻辑是否有对应的测试覆盖？是否依赖真实时间、真实文件系统、真实网络或难以替换的全局状态？若已读取 `spec.md`，测试是否体现其验收标准？
   - **失败显式原则**：是否区分业务失败与系统故障？是否滥用异常做业务控制流？`Result<T, Error>` / `std::expected<T, E>` / 异常的边界是否清晰？错误信息是否可诊断？
   - **极简与演进**：是否存在过度设计、过度抽象、过度模板化、宏滥用或为假设中的未来需求预留的无用代码？
   - **资源管理**：是否符合 RAII？是否存在裸 `new/delete`？智能指针所有权是否清晰？文件句柄、socket、线程、锁、SDK 资源是否可靠释放？
   - **并发与性能**：是否存在数据竞争、死锁风险、异常安全问题、不必要拷贝、频繁分配或为了性能牺牲可读性但无证据支撑？
   - **构建与平台边界**：CMake target 是否清晰？是否使用 target-based CMake？Qt 类型、Signal/Slot、QObject 生命周期是否只停留在合适边界？
6. **输出报告**：
   - 严格使用下方约定的 Markdown 格式输出。
   - 在报告中显式说明本次审查依据、已读取文档、关键假设和无法下结论之处。
   - 对依据不足的部分必须明确写出“不足以下结论”；若已影响合并判断，必须写明“不足以下合并结论”。

- 【列出本次已读取的文档，如 `constitution.md` / `AGENTS.md` / `spec.md` / `plan.md`】

### 总体评价

### 亮点与优点
- 【列出 0~3 个符合宪法或设计精良的代码亮点；若无明显亮点，可明确写“本次未发现值得单列的亮点”】

## 审查规则 (Agent 行为约束)
- **宪法至上**：以 `constitution.md` 为最高准则，任何审查意见不得与其冲突（特别是真理原则与失败显式原则）。
- **治理与事实双重裁决**：同时遵守 `constitution.md` 与 `AGENTS.md`；涉及业务规则、验收与技术方案时，再受 `spec.md` / `plan.md` 约束。
- **事实先于判断**：涉及业务规则、统一语言、验收标准与架构边界时，应优先引用 `spec.md` / `plan.md`；没有依据时必须显式保留判断。
- **全局视野**：切忌脱离上下文进行教条式审查；遇到不确定的依赖关系，主动使用 `Grep` 查询。
- **边界清晰**：用户未指定范围时先澄清，不得擅自扩大审查范围，也不得把通用请求误判为 C++ 审查。
- **停止疑惑**：若关键歧义已影响验收、分层判断或合并结论，必须先澄清或提示补充文档，不得强行给出确定性结论。
- **知其所以然**：每个指出的问题必须说明“为什么”，并关联到具体的工程原则。
- **建设性**：审查建议必须是“可执行的”，尽量提供修改后的代码片段，拒绝空泛表述。
- **显式不确定性**：证据不足时必须写明假设、限制和无法下结论的部分，禁止凭经验补全业务事实。
- **避免教条化**：不因为“现代 C++”而强行引入复杂模板或抽象，不把性能优化建议建立在无证据猜测上。
- **客观无偏见**：优先指出高风险问题，如资源泄漏、悬垂引用、数据竞争、死锁、越界访问、异常安全问题、分层依赖倒置与无法测试的核心逻辑；如果没有明显问题，必须明确告知用户。

## 目标
作为开发者的严师益友，在不越权、不臆断的前提下，帮助 C++ 代码更合宪、更清晰、更安全、更易测、更易维护，并降低资源、并发、生命周期和架构边界风险。
