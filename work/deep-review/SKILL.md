# Deep Review

**核心原则：** 不验证需求的审查不完整。不读全部代码的审查不诚实。

## When to Use

- Feature完成、PR就绪、复杂逻辑需要第二双眼睛
- 计划写完、编码前验证可行性
- 设计文档完成、架构决策做出后
- QA验收前的系统检查

## 审查类型

| 类型 | 何时使用 | 重点 |
|------|----------|------|
| **code** | Feature完成、PR就绪 | 实现质量+功能+安全 |
| **plan** | 计划写完、编码前 | 任务分解+可行性 |
| **design** | 设计文档完成 | 架构+权衡+领域一致 |
| **project** | 大型方案 | 范围+风险+依赖 |

## 五维评分

| 维度 | code | plan | design | project |
|------|:---:|:---:|:---:|:---:|
| 完整性 | ★★★ | ★★★ | ★★☆ | ★★★ |
| 正确性 | ★★★ | ★★☆ | ★☆☆ | ★☆☆ |
| 一致性 | ★★☆ | ★★★ | ★★★ | ★★☆ |
| 安全性 | ★★★ | ★★☆ | ★★☆ | ★☆☆ |
| 可交付性 | ★★☆ | ★★★ | ★☆☆ | ★★★ |

- **完整性** — 需求覆盖矩阵：每个需求追溯到实现
- **正确性** — 逻辑、边界、异常路径、并发
- **一致性** — 与已有代码/规范/术语/ADR
- **安全性** — 注入、TOCTOU、权限、敏感数据
- **可交付性** — 测试覆盖、文档、部署影响、回滚

## 流程

1. 准备输入 — diff 或文档路径 + 需求来源
2. 执行审查 — 生成：需求覆盖矩阵、问题(Critical/Important/Minor)、安全评估、测试评估、裁决
3. 处理结果 — Critical必修 | Important尽快 | Minor记录

## 红线

- 不因"太简单"跳过审查
- 不忽略Critical
- 不接受不含需求覆盖矩阵的审查
