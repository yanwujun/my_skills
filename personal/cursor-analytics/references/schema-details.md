# Cursor state.vscdb Schema Details

## Full table listing

```
Tables: ['ItemTable', 'cursorDiskKV']
  ItemTable: ~1,500 rows (VSCode standard key-value store)
  cursorDiskKV: ~265,000 rows (Cursor-specific AI data)
```

## cursorDiskKV key categories (full breakdown)

### 1. composerData:<composerId> (~1,800 entries)
Session-level metadata. Each composer = one conversation session.

JSON structure:
- `composerId`: UUID
- `createdAt`: Unix timestamp in milliseconds
- `unifiedMode`: "chat" or "agent" (or "plan", "debug")
- `text`: Initial prompt / session name
- `context.fileSelections[]`: Files attached to the session
- `conversationMap`: Container for message bubbleIds (often empty — messages are stored independently)

### 2. bubbleId:<deviceId>:<bubbleId> (~100,000 entries)
Individual messages within conversations. The deviceId is a per-machine UUID.

Each bubble is a JSON object:
- `type`: 1 = user, 2 = assistant
- `text`: Plain text content
- `richText`: LEXICAL editor format (structured)
- `createdAt`: ISO 8601 string (e.g., "2025-11-28T07:38:32.068Z")
- `bubbleId`: Self-referencing UUID
- `requestId`: Groups bubbles within a single request/response pair
- `workspaceProjectDir`: Project path (Windows format: `c:\Users\...\projects\...`)
- `unifiedMode`: Mode code (2 = agent)
- `thinking`: For assistant messages, contains `{text, signature, thinkingStyle, thinkingDurationMs}`
- `tokenCount`: `{inputTokens, outputTokens}` — often 0 (not always recorded)
- `context`: File selections, terminal selections, etc.
- `suggestedCodeBlocks[]`: Code generated by the assistant
- `codeBlocks[]`: Code blocks in the response
- `mcpDescriptors[]`: MCP tool invocations

### 3. agentKv:blob:<hash> (~130,000 entries)
Opaque agent state blobs. Usually not human-readable.

### 4. codeBlockDiff:<deviceId>:<diffId>
Code diffs generated during agent sessions.

### 5. checkpointId:<deviceId>:<checkpointId>
Git-like checkpoints for code changes.

### 6. messageRequestContext:<deviceId>:<bubbleId>
Request-level context for each message exchange.

### 7. inlineDiff:<workspaceHash>:<diffId>
Inline code diffs for specific workspace files.

### 8. composerData duplicates with different keys
The same composer may appear under different device IDs. The `000c7693...` device is typically the primary machine.

## Rich text extraction

When `text` is empty, extract from `richText`:

```python
rt = data.get('richText', {})
text = ''
for child in rt.get('root', {}).get('children', []):
    for c in child.get('children', []):
        if c.get('type') == 'mention':
            pass  # file references — skip or extract mentionName
        elif c.get('text'):
            text += c['text']
```

## Timestamp handling

- `composerData.createdAt`: Unix ms (e.g., 1750057033933)
- `bubbleId.createdAt`: ISO 8601 string (e.g., "2025-11-28T07:38:32.068Z")

## Device ID mapping

The `bubbleId` key format is `bubbleId:<deviceId>:<bubbleUUID>`. 
Device IDs are per-Cursor-installation UUIDs. The one with most entries is the primary development machine.

Top device IDs by bubble count (example from real extraction):
- `000c7693-b5ff-4396-b7a8-3bb73fe0412a` — 30 entries (special: main config device)
- `840eb880-eaa9-416d-bb7b-e598211cca03` — 4,559 entries
- `5818fbf8-956d-4860-8ac5-dd2389254ebf` — 3,572 entries
- `55b98698-b58c-467b-a883-df16acda8164` — 2,960 entries

## Performance notes

- The 4GB database takes ~10s to copy
- Full scans of 100k+ rows take 5-30s
- Always filter with WHERE clauses before scanning
- Use `LIMIT` for sampling
- The `key` column is indexed (PRIMARY KEY equivalent)
